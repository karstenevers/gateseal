# Implement tool kinds in the compiler and describe every tool as data

Accepted on 2026-10-27 and implemented. The tool kinds and the built-in tools came first. The team-defined tools and policy-defined capabilities followed after the hold on them was lifted on 2026-11-01, and then capability alternatives and the tool Python, which the gateseal glossary names the Hook Python. This refines the clause of [design record 0002](0002-resolve-one-declarative-policy.md) that capabilities remain implemented by the compiler; the rest of that decision stands.

Every tool gateseal runs used to be compiler code, so each new tool needed a Python change and a gateseal release. Now the compiler implements a few tool kinds, and every tool is a declarative tool definition of one kind. A kind owns how its tools are acquired, verified, isolated, run and version-checked: exact pins, checksum-verified archives or a revision proven by the tool's version output, no host fallback, owned configuration outputs and removed environment overrides. A definition only parameterizes its kind, with a repository, file names, arguments, a version command and the output format gateseal parses. The first kinds are a Python-language pre-commit hook repository and a release binary prepared through mise, and gateseal ships pre-commit-hooks, Ruff and Betterleaks as built-in definitions in the package. A new kind is a compiler change and can arrive in a minor release, since a policy that uses it raises `minimum_compiler`.

The same format later lets a team's policy add team-defined tools of a known kind without a gateseal release. Such a policy defines its capabilities as named sets of tools, offers alternatives as Policy Choices, and may pin the tool Python that its Python-language tools run on, because a tool such as Black parses code with the interpreter it runs on. Built-in names stay reserved, and `status`, `doctor`, `check` and `run` label each tool built-in or team-defined, because a team definition carries only the tool-specific guarantees it declares, such as turning off a scanner's ignore file.

Policies stay data. The compiler loads no code from a policy, no field runs a command outside its kind's declared arguments, and arguments never pass through a shell. Tools run inside pre-commit or as prepared binaries, as before. A policy repository is already trusted with code, because it picks the revisions that every developer's hooks run.

Two alternatives were rejected. One keeps every tool in compiler code, which makes each new tool a gateseal release. The other lets a policy name any pre-commit hook repository or command, which drops the version proof, configuration isolation and findings and turns the policy into a plugin mechanism. Team-defined tools were held at first and not built, because the pilot should first show that a team needs a tool the built-ins lack before the definition format becomes a public contract.
