# Upgrade through one planner and let the candidate render a compiler move

Accepted on 2026-11-01 and implemented.

A Repository Maintainer moves a policy release, a component, or the compiler with `gateseal upgrade`, and rolls back with the same command and an older target. One planner reads a worktree whose Manifest and Lock agree, applies every target, revalidates every Version Exception against the target policy, and writes nothing until all of them hold. A component target edits that component's Version Exception, because the Manifest has no other place to deviate from the policy's pin, and a target without a version follows the pin but keeps a newer version that the policy still reviews. The writes follow configure's ownership rules, and activation runs only when asked, after the writes, so a failed activation keeps the tracked upgrade.

Only a compiler can render its own Lock and outputs, since the runtime record, the tool definitions and the rendering are its code. So a compiler target is planned by the candidate: the current compiler verifies the wheel by SHA-256, installs it with uv in a scratch environment, and runs the candidate's public `configure` and `check` in a scratch repository that holds the Manifest. The current compiler then writes the result under its own ownership rules, from the Lock it validated. The candidate must take the policy and every pin as they are, so a compiler move never moves the policy or a tool to fit; a bundled policy moves with its compiler only when the maintainer asks.

Letting the candidate accept a Lock that another release wrote was rejected, because a rollback to a release that predates the change would then be impossible, and every release would need to read every other release's Lock. A reviewed catalog of compiler releases inside the compiler was also rejected, because it makes each compiler release name its successors and turns review data into code; the wheel URL and SHA-256 are the reviewed data, given as flags.
